# BestPrice — правила работы (оркестратор)

Пользователь описывает задачу в чате. Дальше ты сам идёшь по конвейеру ниже, не спрашивая «что делать дальше». Отвечай по-русски.

Контекст проекта: `docs/PLAN.md` (стек, архитектура, решения), `tasks/prd-*.md` (требования). Перед работой прочитай релевантные части.

## Конвейер

Размер задачи определяет глубину. **Мелкая** (опечатка, текст, правка в одну строку): шаги 4 и 8, остальные пропусти. **Обычная и крупная**: все шаги по порядку.

1. **Найти инструменты.** Skill `find-skills`: проверь, нет ли skill, MCP или готовой библиотеки под задачу. Для документации библиотек используй context7. Для Supabase и Vercel используй их MCP.
1а. **Разведка сайта.** Если задача про парсер (новый магазин, больше товаров, парсер даёт меньше ожидаемого): skill `site-recon` до любых предложений. Через Playwright найти источники данных и скрытый API, посчитать охват, выдать варианты решения. Без отчёта разведки решение не предлагать и код не писать.
2. **Допросить.** Skill `mattpocock-skills:grilling`: задавай вопросы, пока не станут ясны цель, границы и критерии готовности. Если задача новая и большая, перед этим `superpowers:brainstorming`; если нужны формальные требования, `create-prd` (результат в `tasks/`). Не спрашивай то, что видно из кода или `docs/PLAN.md`.
3. **План.** Для многошаговой задачи `superpowers:writing-plans`; коротко покажи план и жди согласия. Для небольшой задачи план в 3–5 строк в чате.
4. **Реализация.** Skill `ponytail` действует всегда (уже включён хуком): минимум кода, stdlib и уже установленное раньше новых зависимостей. Логику (парсеры, цены, сопоставление товаров, RLS) пиши через `mattpocock-skills:tdd`: сначала падающий тест. Баг: сначала `superpowers:systematic-debugging`, потом фикс.
5. **Код-ревью.** Skill `code-review` на готовом diff. Исправь найденное. Спорные замечания проверяй по `superpowers:receiving-code-review`, не принимай вслепую.
6. **Оптимизация.** `ponytail:ponytail-review` (что можно удалить или упростить), затем `simplify`. Применяй только то, что не ломает тесты.
7. **Безопасность.** Skill `security-review`. Особо проверяй: RLS и белый список email, секреты (`.env` не коммитить), ключи Supabase (service role только в парсерах/CI, не в браузере), валидация входных данных парсеров (zod), XSS в выводе названий товаров.
8. **Проверка.** `superpowers:verification-before-completion`: запусти `pnpm lint`, `pnpm build`, `pnpm --filter @bestprice/core test` и тесты затронутых пакетов. Пока нет вывода команд с успехом, не пиши «готово». Если менялся интерфейс, проверь его в браузере (Playwright MCP).
9. **Документация.** Обнови то, что изменилось: `docs/PLAN.md` (архитектура, решения), `tasks/prd-*.md` (статус требований), комментарии к схеме БД и README пакета. Не раздувай: только факты, которые нельзя вывести из кода.
10. **Завершение.** Коротко отчитайся: что сделано, что проверено (с результатами), что отложено. Коммит и push только по просьбе пользователя. Для оформления ветки `superpowers:finishing-a-development-branch`.

## Тесты

- Каждая новая логика получает тест. Стек: `node --test` + `tsx` (как в `packages/core`); для парсеров фикстуры (сохранённый HTML/JSON магазина) вместо живых запросов.
- **Тесты обязательны** на каждую новую функцию и каждое исправление, без исключений для «простого». Нельзя сказать «готово», пока тесты не написаны и не прошли. Если логику автотестом не проверить (SQL, интерфейс за входом), скажи об этом и опиши, чем проверил вместо него.
- Баг сначала воспроизводится тестом, потом чинится.
- Миграции Supabase: проверяй `get_advisors` (security и performance) после изменения схемы.

## Ветки

- Каждая новая функция и каждое исправление делается в отдельной ветке от `main` (`feat/<кратко>`, `fix/<кратко>`). Ветку создаёшь сам перед первой правкой, в `main` напрямую не работаешь. Так любое изменение можно откатить, не задев рабочий код.
- Коммит, push и слияние в `main` только по просьбе пользователя (см. «Жёсткие правила»). Для слияния `superpowers:finishing-a-development-branch`.

## Релиз

- Изменения попадают в `main` только через PR с зелёным CI (`.github/workflows/ci.yml`), никогда прямым push. Полная схема, шаги и откат: `docs/RELEASE.md`. Деплой Vercel запускается сам после слияния в `main`.
- Когда накопилось несколько веток, начни с `pnpm release:plan`: порядок слияния и конфликты. Миграции применяются к боевой БД **до** слияния кода (бэкап, затем apply, затем `get_advisors`) и должны работать со старым кодом (только добавление; удаление и переименование через два релиза).
- Push, создание PR, слияние, миграция в боевую БД и запуск боевых парсеров только после явного подтверждения пользователя. Каждый шаг называй заранее, что именно сделаешь.
- После слияния проверь: тег и релиз созданы, деплой Vercel завершён (статус `Vercel` на коммите или MCP Vercel), страница открывается.

## Версия приложения

- Формат `А.Б.В.Г`, например `1.0.0.0`. Источник правды: файл `VERSION` в корне. Сайт показывает версию в подвале (если подвала ещё нет, это отдельная задача).
- Что увеличивать: **А** смена архитектуры или новый раздел (например, `energy.*`), **Б** новая функция или новый магазин, **В** исправление ошибки, **Г** мелочь без изменения поведения (текст, стиль, документация, рефакторинг). При увеличении числа правее стоящие обнуляются.
- Версию поднимаешь сам в той же ветке, где сделана работа, и записываешь строку в `docs/CHANGELOG.md` (дата, версия, что и зачем). Не спрашивай разрешения на это.

## Документация

- Ведёшь её всегда, а не «если останется время». Для любого изменения должно быть записано: что сделали, как, почему и что отложили. Архитектурные решения и причины в `docs/PLAN.md`, требования и статусы в `tasks/prd-*.md`, хронология в `docs/CHANGELOG.md`.
- Документы пишутся так, чтобы по ним можно было понять устройство проекта и внедрить новую функцию правильно, не перечитывая весь код. Только факты, которые нельзя вывести из кода.

## Журнал ошибок (`docs/findings/`)

- **Нашёл и исправил собственную ошибку** (ошибку в своём коде, не в чужом): создай `docs/findings/ГГГГ-ММ-ДД-кратко.md` с разделами: что случилось; почему возникла; как исправлено; как изменения повлияли (или не повлияли) на остальной код; как не допустить снова. Добавь строку в индекс `docs/findings/README.md`.
- **Перед работой над любой проблемой, ошибкой или падающим тестом** сначала просмотри `docs/findings/` (индекс и поиск по симптомам): возможно, такая уже была, и причина и способ проверки известны. В отчёте скажи, нашлось ли что-то похожее.

## Новый парсер: выпуск (чек-лист)

Парсер не считается законченным, пока он не будет запускаться сам в GitHub Actions. Когда парсер написан, проверен тестами и живым прогоном, сразу сделай и отметь в отчёте:

1. **Job в `.github/workflows/scrape.yml`** по образцу существующих: checkout, pnpm, Node 24, `pnpm install --frozen-lockfile`, `pnpm --filter @bestprice/scraper-<магазин> scrape` с `NEXT_PUBLIC_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` из секрета, выгрузка `debug/` артефактом при сбое. Добавь `timeout-minutes` (время живого прогона с запасом вдвое).
2. **`pnpm-lock.yaml` обновлён** (`pnpm install`) и содержит пакет парсера, иначе `--frozen-lockfile` в CI упадёт.
3. **Настройки:** секрет `SUPABASE_SERVICE_ROLE_KEY` есть в GitHub (`gh secret list`); в `public.sources` есть строка магазина, её `slug` совпадает с `SLUG` в `run.ts`, `enabled = true`.
4. **Расписание** срабатывает только на `main`: до слияния job сам не запустится. Учти время и нагрузку (первый прогон долгий, дальше короче).
5. **После слияния в `main`** (по просьбе пользователя) запусти вручную `gh workflow run scrape.yml`, дождись зелёного прогона, проверь строку в `scrape_runs` и данные на сайте. Предупреди, что письмо при сбое (FR-15) приходит через уведомления GitHub владельца.
6. **Риски CI** запиши в `docs/PLAN.md`: время прогона, возможная блокировка IP GitHub магазином, запасной вариант (запуск с ПК, см. FR-31).

## Проверка исполнением

- `pnpm lint`, `pnpm build` и типы не ловят ошибки исполнения (например, серверный код получил значение из клиентского модуля). Перед словом «готово» запусти код или страницу вживую. Если вход не пройти (Google), прогони те же запросы и функции скриптом на реальных данных и прямо скажи, чего не проверил.
- Правки файлов делай инструментом Edit. Скрипты через heredoc теряют обратные слэши, а многострочные замены не срабатывают в файлах с CRLF.

## Жёсткие правила

- Необратимое или внешнее (удаление данных, применение миграций к боевой БД, деплой, push, смена переменных в Vercel/Supabase) только после явного подтверждения пользователя.
- Перед миграцией и перед первой массовой записью в боевую БД делай бэкап данных в `backups/ГГГГ-ММ-ДД-<причина>/` (в `.gitignore`, внутри есть email) вместе со скриптом отката. Пример: `backups/2026-10-27-before-offers-scale/`.
- Секреты не печатать, не коммитить, не логировать.
- Не добавлять зависимости, если хватает стандартной библиотеки или уже установленного.
- Изоляция разделов (`grocery.*`, позже `energy.*`): не смешивать схемы и пакеты, см. `docs/PLAN.md`.
- Если шаг конвейера пропущен, скажи об этом и почему.
