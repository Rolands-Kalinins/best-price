# Жёсткий потолок `limit=1000` в парсере Maxima

**Что случилось.** Первый запуск `scrape.yml` на GitHub после релиза 1.1.0.0: job `maxima` упал с «получено 1000 из 1136 акций, лимит запроса мог измениться». Сначала это выглядело как блокировка Cloudflare (риск, о котором мы предупреждали), но данные пришли.

**Почему.** Когда писался парсер, акций было 878, и я записал допущение «`limit=1000` отдаёт все акции за раз» в константу и в документацию. К 27.10 акций стало 1136: сервер отдал ровно 1000 (сколько просили), а `totalItems` сказал 1136. Потолка в 1000 у API нет, `limit=2000` и `limit=5000` отдают все 1136. Проверка полноты в `scrape()` сработала правильно и остановила запуск вместо тихой потери 136 акций.

**Как исправлено.** `limit=5000` (запас в 4 раза), проверка `получено < totalItems` осталась: если акций станет больше 5000, запуск снова упадёт громко. Тест воспроизводит сбой: мок-сервер ведёт себя как настоящий (отдаёт не больше `limit`, `totalItems` = 1136), со старым значением он красный.

**Влияние на остальной код.** Только константа адреса Maxima, формат ответа тот же. Остальные парсеры не затронуты.

**Как не допустить.**
- Число, взятое из наблюдения за сайтом («все 878 акций за один запрос»), не зашивать как потолок: брать запас и оставлять проверку полноты по счётчику сайта (она здесь и спасла данные).
- Падение парсера в CI разбирать по журналу, а не по предположению о причине: «Cloudflare» оказался неверной догадкой.
