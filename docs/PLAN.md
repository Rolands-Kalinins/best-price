# BestPrice — план проекта

Закрытый pet-проект для себя, семьи и друзей (до 20 человек). Сбор акций из магазинов Латвии. Без заработка. Интерфейс на русском, названия товаров в оригинале (латышский).

## Стек (всё бесплатно)

| Слой | Выбор |
|---|---|
| Фронтенд | Next.js (App Router), Tailwind, shadcn/ui, Vercel Hobby |
| БД и авторизация | Supabase free: Postgres, Google OAuth, RLS. Запросы через `supabase-js` и сгенерированные типы, без ORM |
| Парсеры | TypeScript, `fetch` + cheerio, валидация zod. Playwright только если сайт без него не открывается |
| Запуск парсеров | GitHub Actions по cron в 22:17 UTC (00:17 Рига зимой); GitHub опаздывает на 5–6 ч, ночной запуск гарантирует свежие данные к утру. **Четыре группы cron** (лимит 2000 минут в месяц на приватный репозиторий; в ноябре 2026 при запуске всего каждую ночь уходило ≈140 мин в сутки, Apotheka 40%, Euroaptieka 24%, Rimi 20%): каждую ночь лёгкие парсеры (22:17), Lidl раз в неделю (22:47, воскресенье UTC = ночью на понедельник: буклет действует пн–вс, следующий выкладывают с пятницы; при сбое повтора до следующей недели нет, админ запускает вручную), Rimi четыре ночи в неделю (22:27, вс/вт/ср/сб UTC: акции Rimi стартуют по пн/ср/чт/вс), Apotheka и Euroaptieka трижды в неделю (22:37, вс/вт/чт UTC = ночью на пн/ср/пт; сроков акций в данных нет), причём Apotheka по воскресному cron читает и карточки рецептурных (`APOTHEKA_CARDS`, `scrape({cards})`), а по вт/чт только список (≈20 из 57 мин). Окно свежести аптек на сайте 8 суток (`STALE_DAYS` в `core/pharmacy-view.ts` и `pharmacy.group_members`, миграция `20261113100000_pharmacy_fresh_8_days.sql`; было 3). Условие `github.event.schedule == '<cron>'` в `if:` каждого job'а должно совпадать с cron дословно. Ручной запуск (`source = all` или конкретный) запускает всё как раньше. `concurrency` у каждого cron своя (`scrape-<cron>`): в одной группе ждёт один запуск, и новый отменял бы прежнего, а в ночь на понедельник совпадают четыре cron. Расписание магазинов лежит в `core/scrape-schedule.ts` (`SHOP_CRONS`, тест сверяет со `scrape.yml`); из него страница берёт «следующее обновление» и порог «данные устарели» (`staleAfterHours`: пауза + сутки). Данные аптек могут отставать до 3 суток; пропавший из каталога товар аптеки висит на сайте до 8 суток. Известное ограничение: у товаров продуктовых магазинов без даты окончания окно 3 суток (`STALE_DAYS` в `offer-view.ts`), пауза Rimi до 3 суток — таких акций единицы (4 у Rimi на 2026-11-13) |
| Репозиторий | Один приватный monorepo, pnpm workspaces: `apps/web`, `packages/core`, `packages/scrapers/*` |

## Архитектура

Изоляция отказов, а не отдельные серверы:

- Общее ядро: `users`, `sources`, `scrape_runs`.
- Каждый раздел: своя схема БД (`grocery.*`, позже `energy.*`), свой модуль во фронтенде, свой пакет парсеров.
- Разделы подключаются через один файл-реестр. Скрипт `pnpm new-module` создаёт шаблон нового раздела.
- Упал парсер — сайт работает. Каждый запуск пишется в `scrape_runs`. У каждого магазина метка «обновлено X назад». Устаревшие акции скрываются по дате окончания. О сбое уведомляет GitHub Actions по email. Журнал пишет общий `runScrape` (`core/src/scrape-run.ts`): `run.ts` парсера только преобразует строки и пишет их в таблицу.

## Окружения

- **Прод:** облачный проект Supabase `best-price` (Vercel, парсеры в GitHub Actions). Бесплатный тариф даёт 2 активных проекта (оба заняты: `finance-helper`, `best-price`), а ветки БД платные, поэтому второго облачного проекта нет.
- **Разработка:** локальный Supabase в Docker (`pnpm db:start`, `pnpm db:reset`). Миграции из `supabase/migrations` применяются сами, `supabase/seed.sql` заводит тестового админа `dev@bestprice.local` / `dev-password-123` (пароль публичный, в облако сид не попадает). Остановка: `pnpm db:stop`. Боевые данные в локальную БД копирует `pnpm db:pull` (только чтение боевой, ключ из `.env.prod`; без `users` и `allowed_emails`): запускать перед проверкой страниц и парсеров, чтобы на localhost было то же, что на Vercel. Тот же скрипт запускает кнопка «Загрузить из боевой БД» на странице «Парсеры» админки (2.10.0.0; только `next dev` с локальным Supabase, `canPullProdData`). `source_id` при копировании переводится по slug: id магазинов в базах разные.
- **Подключение:** `apps/web/.env.local` смотрит на `http://127.0.0.1:54321` с локальным publishable-ключом (`pnpm db:status` покажет ключи). Форма входа по паролю есть только при `NODE_ENV=development` (`apps/web/app/login/page.tsx`), в боевой сборке её нет.
- **Данные:** локальная база пуста; парсер пишет туда, если подставить локальные `NEXT_PUBLIC_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` (корневой `.env` с боевым ключом перекрывать нельзя: `--env-file-if-exists` читает его, но переменные окружения оболочки приоритетнее).
- **Миграции:** сначала на локальной базе (`pnpm db:reset`), потом бэкап и применение к проду (см. `docs/RELEASE.md`).

## Доступ

- Вход только через Google; любой вошедший = `member` (с 2.8.0.0 `public.is_member()` проверяет только наличие email в JWT, миграция `20261102100000_open_signup.sql`). Админы задаются в `allowed_emails` (роль `admin`, подхватывается триггером `handle_new_user` при первом входе; уже созданным пользователям роль меняется в `public.users`). Аноним не видит ничего: `anon` без `execute` на функции и без grants на таблицы. Риск: любой Google-аккаунт читает цены и грузит БД; личных данных в таблицах нет, `users` читается только своя строка. Если понадобится закрыть: вернуть `is_member()` к проверке `allowed_emails`.
- Vercel: Standard Protection закрывает все `*.vercel.app`, кроме кастомных доменов, поэтому у проекта `web` добавлен домен `bestprice-live.vercel.app` (как `finanse-helper-live`). В Supabase Auth → URL Configuration Site URL и Redirect URLs должны содержать этот адрес, иначе после входа редирект уходит на старый.
- Заголовки безопасности (2.13.1.0, `apps/web/security-headers.ts`, подключены в `next.config.ts`): CSP, `frame-ancestors 'none'` (запрет встраивания), nosniff, Referrer-Policy, HSTS (не в dev). `script-src` с `'unsafe-inline'`: nonce заставил бы рисовать каждую страницу заново. `img-src https:`: картинки грузятся прямо с сайтов магазинов, набор доменов растёт. Новый внешний источник (шрифт, скрипт, API) надо добавлять в CSP, иначе браузер его заблокирует.
- Роли: `admin` (владелец) и `member`.
- Избранное и список покупок у каждого свои. Общие списки позже.
- Журнал `scrape_runs` (статусы, ошибки) виден только админу (RLS); участнику функция `public.last_scrape_success()` отдаёт лишь время последнего успеха для метки «обновлено». Страница `/grocery/admin/scrapers` показывает статус и запускает парсеры через `workflow_dispatch` (`scrape.yml`, вход `source`); токен `GITHUB_DISPATCH_TOKEN` живёт только в переменных Vercel (server action, в браузер не попадает). Ближайший запуск считается из `SCRAPE_CRON` (`core`), номинально: GitHub опаздывает на часы.

## Данные продуктов

- Берём только акции.
- История цен: одна строка в день на товар и магазин, только при изменении цены. Старше 6 месяцев удаляем.
- Даты акции берём из источника (Maxima, Lidl, Etop, Rimi). У Rimi период только на карточке товара: парсер ходит за ней один раз на акцию, дальше берёт период из БД.
- Lidl: весь индекс API (там только акции). Rimi: всё, что лежит на странице акций (старая цена, цена по карте MansRimi, «N un vairāk», EDLP).
- Условие акции («2 шт.») хранится текстом в поле `condition`. В сводке сравниваем цену за единицу (за кг или л), товары с условием помечаем значком.
- Сопоставление товаров (реализовано в 1.3.0.0, `packages/core/src/match.ts`, запуск `packages/matcher`):
  1. **Ключ товара** = бренд | размер в г или мл | условие | отсортированный набор слов названия (без регистра, диакритики, сокращений упаковки). Размер: «2x500g» = 1000 г, «0,33L» = 330 мл. Бренд ищется в названии по словарю брендов из полей `brand` магазинов (Etop 94%, Lidl 71%; у Rimi и Maxima поля нет); не нашёлся, а поле есть, берётся оно. Нет бренда или размера: товар не сопоставляется.
  2. **Условие**: карта магазина (PALDIES, MansRimi, top!, Lidl Plus) условием не считается, цена по ней идёт в карточку с бейджем. Различаются «от N шт.» (`minN`) и «цена за набор из N» (`setN`). «Любые 2 товара» не сопоставляется. Акции на несколько товаров («COCA-COLA, FANTA vai SPRITE, четыре вида», слова vai/veidi) и скидки на бренд без цены не сопоставляются.
  3. **Автоматически** объединяется только точное совпадение ключа у акций минимум двух магазинов. **Предположение** (очередь админа `/grocery/admin/matches`): тот же бренд, размер и условие, доля общих слов ≥ 0,6 (Жаккар). На 2026-10-28: 62 товара, 78 предположений. Решение админа хранится в `grocery.match_decisions` по паре ключей (не по id акции: ключ Maxima меняется каждую неделю), «Тот же товар» склеивает ключи, «Разные» гасит предположение. Ключ группы = наименьший из склеенных, поэтому строка `products` не «переезжает».
  3а. **Правило сокращений (2.11.0.0, `softEqual` в `match.ts`):** в одной корзине (бренд | размер | условие) ключи, у которых слова различаются только сокращением с точкой в названии (`abbrTokens`) или падежным окончанием из `ENDINGS` (общее начало ≥ 4 букв), объединяются без админа и Gemini. Все различающиеся слова должны попарно совпасть: лишнее слово не склеивается. Решение админа по паре, в том числе «разные», сильнее правила; склейка не соединяет группы, между ключами которых есть «разные» (2.11.1.0). Если админ сам склеил ключи через третий и этим нарушил своё «разные», `buildMatches` возвращает это в `conflicts`, матчер пишет предупреждение. Префикс без точки (`kaf`→`kafija`) не правило: на данных 1 ложная склейка из 2 (Milka Choc&Choc / Chocominis). Что проверено и отвергнуто: словарь шумовых слов небезопасен (спрей и обычный кондиционер — разные товары), правило «по одному сироте с каждой стороны» даёт много ложных склеек (разные вкусы одного бренда). Автопринятие (2.12.0.0): пара из очереди принимается без админа, если Gemini сказал «тот же» и вторая проверка (`pair_checks`, `checkPrompt`, `acceptedPairs` в `ai.ts`) не нашла различий; иначе остаётся в очереди. Принятые пересчитываются каждый запуск из кэша ответов (в `match_decisions` не пишутся) и снимаются в «Объединённые товары». Замер: 71 принято, 0 ошибок, 26 осторожных отказов из 104. Кандидаты-сироты (Жаккар < 0,6) пока не делаем.
  4. Результат: `grocery.products` и `offers.product_id`. Пересчёт: `pnpm --filter @bestprice/matcher match` (workflow `match.yml`: после `scrape` и вручную); `dry` только печатает. Решение админа вступает в силу при следующем пересчёте, не мгновенно.
  5. **Лишняя акция в группе:** админ убирает её кнопкой в очереди, id пишется в `grocery.match_exclusions`, `buildMatches` такие акции не берёт ни в группы, ни в предположения; акция остаётся обычной карточкой в ленте. Исключение по id акции (у Maxima id меняется каждую неделю, там убирать придётся заново). Из уже подтверждённого товара акцию тоже можно убрать: вкладка «Объединённые товары» на странице «Сопоставление» (2.9.0.0, `?tab=joined`, по 50 товаров на страницу). Разъединение по варианту (вкус, аромат) пока только через исключение каждой акции; идея на будущее: `offers.match_key` + кнопка «Отделить вариант», пишущая «Разные» в `match_decisions`.
  6. **Gemini (1.5.0.0)** помогает двумя способами, всё в `packages/matcher` (клиент `src/gemini.ts`, `fetch` без SDK; логика промптов и проверки ответов `packages/core/src/ai.ts`). (а) **Бренд из названия** для акций, где магазин его не отдаёт: пачки по 100 названий, ответ по JSON-схеме, температура 0. `acceptBrand` принимает бренд, только если он дословно есть в названии (выдуманный, частичный или подсказанный названием отбрасывается: названия приходят с чужих сайтов, ответу модели не доверяем). Принятый бренд идёт в `brandHint` и в ключ товара, поэтому группы по нему объединяются автоматически, как с брендом из поля магазина. Сорта («Valencia», «Idared») и свежие продукты без бренда промпт велит не считать брендом, на 5 пробных названиях модель один раз ошиблась, второй раз нет: бренд-сорт остаётся риском, его ловит выборка перед первым прогоном. (б) **Совет по предположению**: «тот же товар?» и причина по-русски в одну строку; никого не объединяет, в очереди админа метка «Gemini: вероятно тот же / разные», «вероятно тот же» сверху. Кэш: `grocery.title_attrs` (название в нижнем регистре → бренд, null = «бренда нет») и `grocery.pair_verdicts` (пара ключей), ключ включает `PROMPT_VERSION` (при смене промпта поднять, старый кэш перестаёт использоваться); RLS без политик, доступ только у сервисной роли. Настройки через окружение: `GEMINI_API_KEY`, `GEMINI_MODEL` (по умолчанию `gemini-3.1-flash-lite`), `GEMINI_MAX_REQUESTS` (потолок запросов за запуск, по умолчанию 30; первый большой прогон с ПК ≈60 запросов, ставить 200). Нет ключа, лимит или сбой API: матчер работает с кэшем, сбой пишет `Gemini: …` в лог и запуск не роняет. `pnpm --filter @bestprice/matcher dry` вызывает Gemini, но ничего не пишет в БД, и печатает сравнение «без Gemini / с Gemini», выборку брендов, новые группы и советы. **Учёт квоты (1.6.0.0):** матчер считает все HTTP-запросы к Gemini (с повторами), токены из `usageMetadata` ответа, ошибки и ответы 429 и пишет их в `grocery.ai_usage` через `grocery.add_ai_usage` (день по Лос-Анджелесу: в его полночь, 09:00–10:00 по Риге, Google сбрасывает суточный лимит RPD); страница `/grocery/admin/ai` показывает расход против `grocery.ai_limits` (для `gemini-3.1-flash-lite` по AI Studio на 2026-10-28: RPM 15, TPM 250K, RPD 500; меняются вручную в SQL). API остаток квоты не отдаёт, и лимиты считаются на проект Google, а не на ключ, поэтому счётчик видит только матчер, точный остаток только в AI Studio; ответ 429 — точный сигнал «квота исчерпана». RPM и TPM дневной счётчик не проверяет, они показаны справочно. Бесплатный уровень Google использует отправленное для улучшения продуктов: отправляем только публичные названия товаров, без email и запросов пользователей. Модели Google быстро устаревают (старые имена переводятся на новые автоматически): имя держим в переменной, доступные модели ключа: `GET /v1beta/models`. Ограничения: пропущенный моделью индекс кэшируется как «бренда нет»; в запрос совета идут первые 6 акций предположения.
  7. Ограничения: бренд, которого нет в полях Etop и Lidl и который не распознала модель, не распознаётся (потерянные совпадения Rimi с Maxima); разные сокращения («Gāz.dz.» и «Gāzēts dzēriens») дают предположение, а не совпадение; сравниваются акционные цены на сегодня, каталога без акций у магазинов нет.
- Общие категории (1.7.0.0, фильтр «молочные», «мясо» и т.д.): ~20 крупных категорий (еда и не еда: бытовая химия, косметика, дом, животные, одежда, сезонное) лежат в коде, `packages/core/src/categories-data.ts`: slug, русское название и латышские основы слов (без диакритики, «^» = с начала слова). Раскладывает код (`categorize` в `category.ts`), Gemini на это не тратится: он один раз предложил список и основы (5 запросов: сначала категории по выборке 700 названий, затем 4 круга «дополни основы для названий без категории»), дальше основы чистились и дополнялись вручную. Решение «код, а не Gemini на каждый товар» принято из-за квоты (500 запросов в сутки) и потому что акции приходят каждую неделю: словарь работает бесплатно и для новых товаров.
  - **Правила:** текст = название + сырая категория магазина (у Etop и Lidl она словесная и сильный признак; коды Rimi `SH-…` ничего не дают). Побеждает самая длинная основа («piena šokolāde» — сладости, а не молочное), при равенстве выше категория в списке. Ничего не нашлось — `other` («Другое»).
  - **Где хранится:** `grocery.offers.cat` (slug; null = ещё не раскладывали). Ставит шаг `pnpm --filter @bestprice/matcher categorize` (workflow `match.yml`, шаг после сопоставления, выполняется и после его сбоя), пишет только изменившееся, поэтому повторный запуск безопасен, а правка словаря перераскладывает всё при следующем запуске. Парсеры `cat` не трогают. `categorize --dry` печатает охват по категориям и частые слова без категории: по ним дополняют словарь.
  - **Качество (первый прогон на боевых данных, 6674 акции):** без категории осталось ~1,7% (116), «Другое» — единицы. Точность не мерили строго; по выборке по 10 названий на категорию ошибок порядка 10%: чаще всего фрукт или овощ внутри готового продукта («Rūdolfs каша с черникой» — овощи), «piena dzēriens» — напитки, бренд в названии другого товара. Ограничение подхода: основа общего слова даёт ложные срабатывания, поэтому такие слова убирались (`lidzekl`, `konserv`, `pasta`, `zelej`, `kapsul`). Если ошибок станет заметно больше: добавить основу и прогнать `categorize`, при необходимости отдавать «Другое» одним запросом Gemini.
  - **Фильтр:** чипы категорий над лентой (одна прокручиваемая строка), параметр `?cat=<slug>` (в `parseQuery` неизвестный slug отбрасывается). Фильтр применяется и к ленте, и к карточкам «Где дешевле» (по `cat` акций товара).
- Главная раздела: поиск, затем «товар → цены в магазинах» для сопоставленных и список свежих акций по магазинам для остальных. Фильтры по магазину и по значку «с условием».

## Фронтенд

- `/` ведёт участника на `/grocery`, отдельной главной нет. Не из списка видит «Доступ закрыт»; на `/grocery` его тоже возвращают на `/`.
- Mobile-first. Светлая и тёмная темы по `prefers-color-scheme`, переключателя нет. Токены цвета в `app/globals.css`: зелёный `--primary` (выгода и действия), `--sale` только для скидки.
- Лента `/grocery`: одна общая сетка карточек (2/3/4 колонки), не секции по магазинам. Поиск, чипы магазинов, чипы категорий (1.7.0.0), «С условием», сортировка.
- Состояние фильтров живёт в адресе (`?q=&store=&cat=&cond=1&sort=`) и читается через `useSearchParams`; пишется `history.replaceState`, чтобы поиск не перезапрашивал сервер на каждую букву.
- Логика показа (скидка в %, фильтр, сортировка, разбор адреса, проверка ссылок) лежит в `packages/core/src/offer-view.ts` с тестами. UI тонкий.
- Картинки товаров обычным `<img loading="lazy">`, не `next/image`: лимит оптимизации на Vercel Hobby. Ссылки и картинки из парсера пропускаются только если `http(s)` (`safeHttpUrl`).
- Поиск по-русски (1.4.0.0): `searchGroups` в `packages/core/src/offer-view.ts` раскрывает русское слово в латышские основы из словаря `ru-lv.ts` (ключ = начало слова, побеждает самый длинный, ё = е). Слово даёт группу вариантов (`or`), группы связаны «и». Основы только a-z (и пробел внутри) от 3 символов: они идут в `or()` PostgREST, где запятая и скобки ломают запрос, и ввод пользователя в `or()` не попадает (тест это проверяет; `^` из ввода убирается). Основа с `^` ищется с начала слова (`searchOrClause`: `x%` или `% x%`), без неё как подстрока: латышские составные слова («biezpiens», «krēmsiers», «baltmaize») иначе потерялись бы. Короткую основу без `^` перед добавлением прогонять по данным: «sula» находила «kapsulas». Алкоголя в акциях почти нет (реклама ограничена), его основы ничего не находят. Ограничения: «pien» находит и «biezpiens»; «griki» цепляет «GRIKIOS»; «milti» и «smiltis»; общие слова («мясо» → `gala`) при поиске «куриное мясо» требуют обоих слов и могут дать 0; слов вне словаря нет. Пополнять словарь по запросам без результата (когда появится их лог).
- Фильтрация на клиенте, пока акций сотни. Серверная фильтрация и пагинация нужны к этапу 3: PostgREST отдаёт не больше 1000 строк, лишнее молча обрезается.
- Страница ловит ошибки запросов и показывает `error.tsx` («Повторить»), а не ложное «нет данных».

Правила парсера:

- Один запрос в секунду, один запуск в сутки, кэш ответов.
- Честный User-Agent (например `BestPriceBot (личный проект)`), соблюдение robots.txt.
- Защиту не обходим. Если магазин блокирует честный User-Agent, он уходит в ручной режим или «позже».
- Если GitHub Actions блокируется (вероятнее у Maxima), этот парсер запускается с ПК владельца через Windows Task Scheduler и пишет в Supabase.
- Сырые данные сохраняем только при сбое, как артефакт GitHub Actions на 7 дней. В БД они не попадают.
- Данные от парсера проходят валидацию zod до записи в БД.
- Риски CI у Barbora: прогон ≈8 с (`timeout-minutes: 10` с запасом); внутренний `/proxy/api/v1` без версии и обещаний стабильности (защита: zod, порог отброшенных 5%, полнота по `count`); страницы по `Offset` сдвинулись бы, если каталог меняется посреди прогона (за 8 с не наблюдалось, при потере позиций `count` не сойдётся и запуск упадёт); блокировка IP GitHub не проверялась (перед сайтом Cloudflare, честный `BestPriceBot` с ПК пропускается). Запасной вариант: запуск с ПК (FR-31). Разведка 2026-10-31 не проверила: `Limit=500`, смысл `Depth`, зависимость цен от `shopCode=R600`, поведение при частых запросах.
- Риски CI у e-LaTS: прогон ≈15 с (`timeout-minutes: 10` с запасом); разметка плиток не обещана стабильной (защита: zod, порог отброшенных 5%, минимум 200 акций против 438 обычных, потому что страница с ошибкой и кодом 200 выглядит как конец списка); блокировка IP GitHub подтвердилась (403, см. ниже); не проверено, зависят ли цены от выбранного пункта выдачи (Imanta, Mežciems, Purvciems). Запасной вариант: запуск с ПК (FR-31).
- **Запуск e-LaTS с ПК (с 1.12.0.1, FR-31).** Первый боевой запуск в Actions 2026-10-31 дал `e-latts: HTTP 403`: сайт блокирует адреса GitHub (с домашнего адреса тот же запрос с `BestPriceBot` отвечает 200). Защиту не обходим. Job `e-latts` в `scrape.yml` теперь только ручной (`workflow_dispatch`, `source=e-latts`) и в ночной «all» не входит, чтобы не слать ночные письма о сбое. Парсер идёт с ПК: `scripts/scrape-e-latts.ps1` (ключи из `.env.prod` кладёт в окружение процесса, журнал `packages/scrapers/e-latts/debug/pc-run.log`), ночью задача Планировщика Windows «BestPrice e-latts» в 23:30, до ночного `scrape` в Actions (≈00:17 по Риге), чтобы матчер после него видел свежие акции; пропущенный запуск выполняется при включении ПК. Сбой пишется в `scrape_runs` (админка), письма нет: FR-15 работает только для Actions. ПК должен быть включён. Первый боевой запуск с ПК: 438 акций, 0 отброшено.

  Создать задачу один раз (PowerShell, от своего пользователя):

  ```powershell
  $a = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-NoProfile -ExecutionPolicy Bypass -File "C:\Projects\BestPrice\scripts\scrape-e-latts.ps1"' -WorkingDirectory 'C:\Projects\BestPrice'
  $t = New-ScheduledTaskTrigger -Daily -At '23:30'
  $s = New-ScheduledTaskSettingsSet -StartWhenAvailable -ExecutionTimeLimit (New-TimeSpan -Minutes 15) -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries
  Register-ScheduledTask -TaskName 'BestPrice e-latts' -Action $a -Trigger $t -Settings $s -Force
  ```

  Проверка: `Start-ScheduledTask 'BestPrice e-latts'`, затем последняя строка `packages\scrapers\e-latts\debug\pc-run.log` и `exit 0`. Удалить: `Unregister-ScheduledTask 'BestPrice e-latts' -Confirm:$false`.

## Буклеты магазинов (Gemini, с 1.9.0.0)

В буклетах акций больше, чем на сайтах (Lidl: в API 71 товар). Структурированных данных нет, поэтому страницы-картинки читает Gemini (vision) и пишет в `grocery.leaflet_offers` (одна таблица на все магазины, магазин в `source_id`). Таблица не смешивается с `grocery.offers`: данные с картинки надёжнее проверять сравнением с ценами сайта, чем объединять. Пока готов только Lidl (`packages/scrapers/lidl/src/leaflet*.ts`, skill `.claude/skills/lidl-leaflet`, job `lidl` в `scrape.yml`).

- **Lidl читается только по буклету (решение владельца 2026-10-31).** В буклете 240+ акций, на сайте ~70, поэтому парсер сайта (`run.ts`, скрипт `scrape`) в CI больше не запускается; job `lidl` в `scrape.yml` запускает `leaflet`. Запуск ночной и идемпотентный: прочитанные страницы пропускаются без квоты, новый буклет подхватывается в день появления (с пятницы), упавший на квоте дочитывается следующей ночью; дни выхода буклетов у магазинов разные, расписание под них не нужно. **Как буклет попадает на сайт:** в конце запуска действующие записи `leaflet_offers` зеркалятся в `grocery.offers` (`siteOffers` в `packages/core/src/leaflet-view.ts`), поэтому лента, категории (`categorize`), сопоставление и сравнение цен работают как для любого магазина, ничего в них не менялось. Правила: цена по карте Lidl Plus становится ценой акции, обычная идёт в «было», условие «Lidl Plus»; акции без цены и процента («2+1») сайту не показать (check `offers_price_or_discount`), они остаются только в `leaflet_offers`; одинаковый товар с теми же ценами и сроком на разных страницах склеивается в одну акцию; старые акции Lidl, которых нет в буклете (прежний парсер сайта), закрываются `ends_at = сейчас` (из ленты уходят, история цен остаётся). Ссылки на страницу буклета у акции нет (`url` пустой: клик по карточке никуда не ведёт, решение владельца). Фото: парсер режет миниатюру из страницы по рамке Gemini (`sharp`, webp ≤320 px, ≈10 КБ) и кладёт в `grocery.leaflet_thumbs` (bytea, читают участники по RLS); `offers.image_url` = `/grocery/img/<source_id>/<external_id>`, отдаёт route `apps/web/app/grocery/img/[source]/[id]/route.ts` (кэш браузера сутки), `safeHttpUrl` пропускает только этот строгий путь. Первая версия брала картинку со страницы буклета на сервере Lidl: 60 страниц по 2400 px разом грузились ненадёжно, часть карточек оставалась без фото. - **Как читаем.** Одна страница = один запрос Gemini со схемой JSON. Все поля схемы обязательны (nullable разрешает `null`): необязательные модель не возвращает (`docs/findings/2026-10-31-leaflet-optional-fields.md`). Названия копируются как напечатаны, без перевода. Цену за кг/л считает код (`unitPrice`), не модель.
- **Недоверие к модели.** Запись отбрасывается и попадает в лог, если у товара нет цены или она выше 10 000 €, нет процента у скидки на категорию, или процент не сходится с ценой и старой ценой (допуск 2 п.п.). Ошибки без старой цены (0,99 вместо 9,99) так не поймать: для этого нужно сравнение с ценами сайта.
- **Даты.** По умолчанию период буклета из `offerStartDate`/`offerEndDate`, на плитке свой срок из баннера блока (`from`/`to` в формате ДД.ММ, вне периода буклета игнорируются). Отбирать «действует всю неделю» можно запросом по `starts_at`/`ends_at`.
- **Квота.** Бесплатный Gemini: 15 запросов в минуту и 500 в сутки (`docs/PLAN.md`, память про лимиты). Пауза 4,5 с между запросами, потолок `GEMINI_MAX_REQUESTS` (в workflow 120). Расход пишется в `ai_usage`. Раз в неделю: два буклета ≈ 85 запросов. Страница ≈ 1450 токенов входа и ≈ 900 выхода.
- **Повторный запуск.** Прочитанные страницы (есть строки в таблице) пропускаются; после правки парсера `--force`. После записи страницы удаляются её строки, не обновлённые этим чтением (модель пишет название по-разному, ключ меняется).
- **Риски CI.** Время: ~15 минут на буклет (пауза и ответ модели), в job `timeout-minutes: 180` (с запасными моделями до ≈90 минут на два буклета). Блокировку IP GitHub у `leaflets.schwarz` и `lidl.lv` не проверяли, первый боевой запуск покажет; запасной вариант — запуск с ПК. Письмо при сбое приходит через уведомления GitHub. Лимит Gemini общий с матчером (до 30 запросов за запуск).

Открытую модель на ПК как следующий план Б не проверяли.

- **Лимиты бесплатного уровня (Google AI Studio, 2026-10-31).** `3.5-flash-lite` и `3.1-flash-lite`: 15 запросов/мин, 250 тыс. токенов/мин, 500/сутки; `3.6-flash` и `3.8-flash`: 5/мин и всего 20/сутки (как запасные бесполезны); Gemma 4 31B: 30/мин, 14,4 тыс./сутки. Gemini иногда отвечает 503 («перегружен»): страница пропускается, три сбоя подряд останавливают запуск, недочитанные страницы добирает повторный запуск без `--force`.

## Админка: акции и боковое меню (с 1.10.0.0)

- **Страница `/grocery/admin/offers`** (только админ): акции любого магазина как их видит сайт (фото, название, объём, условие, цены, срок, когда парсер видел, когда правили), фильтры по магазину, поиск по названию, «и закончившиеся», «только правленные», по 50 строк. «Править» открывает `/grocery/admin/offers/[id]`: название, бренд, объём, условие, цена, было, скидка, срок, ссылка на картинку. Цена за кг/л пересчитывается сама (`parseOfferEdit` в `packages/core/src/offer-edit.ts`, с тестами).
- **Как правка переживает парсер.** Парсеры пишут акции upsert-ом и о правках не знают, поэтому защита в таблице: `offers.locked_fields` (список поправленных полей) и триггер `offers_keep_locked` (миграция `offer_edits`): если обновляет не админ (`public.is_admin()` ложно: парсеры идут под `service_role`), закреплённые поля возвращаются к прежним значениям, остальные обновляются как обычно. Админу разрешён update только перечисленных столбцов (политика `offers_admin_update` и column-level grant). «Снять закрепление» очищает список: следующий запуск парсера вернёт данные магазина. `log_price` сделан `security definer`, иначе правка цены админом падала на записи в `price_history`.
- **Ограничение.** Правка привязана к строке (`source_id`, `external_id`). Если парсер поменял ключ (Lidl: название или цена при перечитывании страницы буклета дают другой ключ), это новая акция и правка на неё не переносится. Картинку можно заменить только ссылкой (загрузки файлов нет).
- **Боковое меню.** `app/grocery/admin/layout.tsx` (шапка, меню, страница справа; вход и роль проверяются и здесь, и на каждой странице) и `components/admin-nav.tsx`: слева на широком экране, лентой над страницей на узком. В меню профиля теперь один пункт «Админка».

## Аптеки и косметика (`pharmacy.*`, `cosmetics.*`, с 2.0.0.0)

Разведка по магазинам: `docs/recon/` (обзор и файл на магазин). Решения владельца от 2026-11-01: берём **весь каталог** (не только акции); категории по смыслу; рецептурное помечаем флагом; магазин, который блокирует парсер, снимаем с сайта, защиту не обходим; Drogas отложен (`robots.txt` закрывает `/api/v2/`, см. `recon/drogas.md`).

- **Схема `pharmacy`** (миграция `20261101100000_pharmacy.sql`): `products` (ключ `source_id + external_id`; `price`, `old_price`, `starts_at/ends_at`, `ean`, `brand`, `category` = путь магазина, `cat` = наша категория, `prescription`, `in_stock`, `last_seen_at`) и `price_history` (одна строка в день, пишется триггером при смене цены, как у grocery). RLS как у grocery: читают участники, пишет только service_role. Магазин = строка `public.sources` с `module = 'pharmacy'`; страницы продуктов фильтруют по `module = 'grocery'` и аптеку не видят. Схема `cosmetics` будет такой же, когда дойдёт до Douglas.
- **Контракт парсера** `productSchema` (`core/src/product.ts`): цена обязательна, `prescription` и `inStock` явные. Не путать с `offerSchema` продуктов (там цена может быть null, есть `unit` кг/л).
- **Категории по смыслу** (`core/src/pharmacy-categories.ts`): medicine, supplements, tea-food, hygiene, skincare, baby, medical, pets. Основы ищутся в пути категории магазина, потом в названии (тот же `categorize`, что у продуктов). `PHARMACY_TO_GROCERY` связывает каждую с продуктовой (health, drinks, beauty, kids, pets; medical без аналога). Запуск: `pnpm --filter @bestprice/matcher categorize --pharmacy [--dry]`; в CI идёт шагом `match.yml` после каждого прогона (с 2.3.1.0; до этого запускали вручную, и на боевой базе категории были пустыми). На Mēness охват 100% (10 220), «other» нет; у нового магазина основы дополнять по `--dry`.
- **Mēness** (`packages/scrapers/meness`): открытый JSON-API `api.e-menessaptieka.lv/api/v2/shop/search/products`, 100 товаров на страницу. **Поиск не отдаёт глубже 10 000 результатов** (Elasticsearch `from + size ≤ 10000`, дальше HTTP 400), а товаров 10 220, поэтому обход идёт пятью ценовыми диапазонами (`price[min]`, `price[max]` в центах), в каждом меньше 10 000; полноту проверяют общий счётчик каталога и счётчик каждого диапазона. Прогон 2026-11-01 в локальную БД: 10 220 товаров, 0 отброшено, ≈5 минут (≈105 запросов по 3.7 МБ). EAN в API нет (`barcode: null` у всех), бренд есть в атрибуте `brand`, период акции в `prices.startsAt/endsAt`, у 4 277 товаров есть старая цена. Категории: у товара несколько деревьев (магазин, Moonmart, подборки), берём самый глубокий путь из меню магазина, иначе из неслужебных деревьев (гигиена и зоотовары в меню верхнего уровня нет).
- **Выпуск Mēness:** job `meness` в `scrape.yml` (ночью в «all» и вручную), `timeout-minutes: 15`. Риски CI: Cloudflare может заблокировать адреса GitHub (с GitHub не проверялось); в этом случае магазин снимаем (FR-66). Строка `sources` и схема в боевой БД появятся только после применения миграций (по подтверждению владельца).
- **Данные устаревают без удаления.** Полный каталог означает, что исчезнувший из магазина товар остаётся в таблице; о его свежести говорит `last_seen_at` (страницы раздела должны скрывать старое). Чистка не сделана.
- **Цена по карте** (с 2.1.0.0): `pharmacy.products.card_price`, `card_condition`, `card_starts_at`, `card_ends_at` (миграция `20261101130000_pharmacy_card_price.sql`), `price` остаётся ценой для всех. В `productSchema` цена по карте не ниже обычной отбрасывается вместе с условием. Mēness: `prices.loyaltyCatalogPromotionPrice` и свой период, условие «Ar karti «Veselība»», 775 из 10 220.
