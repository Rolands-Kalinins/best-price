# Релиз: от веток до боевого сайта

Как изменения попадают в `main` и на сайт. Автоматика лежит в `.github/workflows/ci.yml` и `release.yml`, помощник в `scripts/release.mjs`. Любое внешнее действие (push, слияние, миграция в боевую БД) делается только после подтверждения владельца.

## Схема

```
feat/*, fix/*  →  release/<версия>  →  PR в main  →  Vercel (сам)  →  тег и релиз GitHub
                       │                  │
                    CI зелёный        CI зелёный
                       └── миграции в боевую БД ДО слияния (бэкап → apply → get_advisors)
```

Деплой на Vercel запускается сам при каждом push в `main` (проект `web` подключён к GitHub). Ветки и PR получают превью-деплои.

## Шаги

1. **План.** `pnpm release:plan` показывает ветки с изменениями относительно `main`, порядок слияния и файлы, которые меняют сразу несколько веток (риск конфликта). Порядок: core → миграции → парсеры → сайт → CI → документация (общее раньше зависящих от него).
2. **Релизная ветка.** `git switch -c release/<версия> main`, затем `git merge --no-ff <ветка>` по порядку из плана. Конфликты решаются здесь, а не в `main`.
3. **Версия.** В релизной ветке один раз: `VERSION` и запись в `docs/CHANGELOG.md` (правила номера в `CLAUDE.md`).
4. **CI.** Push релизной ветки запускает `ci.yml`: lint, тесты всех пакетов, сборка, проверка имён миграций и версии. Без зелёного дальше не идти. `pnpm test` и `pnpm release:check` то же самое локально.
5. **Миграции** (если есть). До слияния кода: бэкап в `backups/`, применение к боевой БД, `get_advisors`. Миграция обязана работать и со старым кодом (только добавляем: столбцы, индексы, политики). Удаление и переименование делим на два релиза: сначала код перестаёт использовать, в следующем релизе миграция удаляет. `release:check` предупреждает о `drop`, `rename`, `set not null`.
6. **PR в `main`.** `gh pr create --base main`, шаблон с чек-листом заполняется, `ci.yml` снова зелёный, слияние `gh pr merge --merge` (merge-коммит сохраняет историю релиза).
7. **Автоматика после слияния** (`release.yml`): создаёт тег `v<версия>` и релиз GitHub с заметками из `docs/CHANGELOG.md`; ждёт статус `Vercel` на коммите (успех или сбой деплоя). Сбой любого job присылает письмо GitHub.
8. **После выката.** `gh workflow run scrape.yml` для новых парсеров (по подтверждению), проверка страницы, запись цифр в `docs/PLAN.md`. Сайт за входом проверяем по CSS: боевой CSS должен содержать `prefers-color-scheme:dark` и `--sale` (один раз боевая сборка получила старый CSS, `docs/findings/2026-10-27-stale-css-vercel-cache.md`).

Срочное исправление: ветка `fix/*` от `main`, тот же CI и PR, версия: третье число +1. Релизная ветка не нужна.

## Откат

- **Код:** в Vercel откатиться на предыдущий деплой (мгновенно, без сборки) и сделать `git revert -m 1 <merge-коммит>` отдельным PR.
- **БД:** миграции аддитивны, поэтому откат кода БД не ломает. Откат самой миграции: скрипт из `backups/<дата>-<причина>/`.

## Ограничения (бесплатный приватный репозиторий)

- Защита ветки `main` и обязательные проверки недоступны (GitHub отвечает «Upgrade to GitHub Pro»): правило «в `main` только через PR с зелёным CI» держится на процессе. В `CLAUDE.md` оно записано для Claude, для остальных на дисциплине владельца.
- Миграции в боевую БД из CI не применяются: нужны токен и пароль базы в секретах GitHub и подтверждение владельца. Сейчас их применяет Claude по подтверждению. Автоматизировать можно, когда появится GitHub Environment с обязательным подтверждением (платный тариф).
- Vercel: превью-деплои веток собираются без ключей Supabase (в проекте они заданы только для Production), поэтому в превью вход и данные не работают. Нужные переменные для Preview добавляются в настройках Vercel.
