## 2.12.1.0 — 2026-11-13
- **Экономия минут GitHub Actions** (израсходовано 1829 из 2000 за 1–13 ноября, ≈140 мин в сутки). Расписание разделено на три cron в `scrape.yml`: лёгкие парсеры каждую ночь, Rimi 4 ночи в неделю (акции стартуют пн/ср/чт/вс), Apotheka и Euroaptieka 3 раза в неделю (ночью на пн, ср, пт). Apotheka по понедельничному cron читает и карточки рецептурных (раз в неделю), в ср и пт только список (`scrape({cards:false})`, переменная `APOTHEKA_CARDS`; ≈20 вместо 57 мин). Ожидаемый расход ≈55–65 мин в сутки. Ручной запуск читает всё, как раньше.
- **Окно свежести аптек 3 → 8 суток** (`STALE_DAYS` в `pharmacy-view.ts`, миграция `20261113100000_pharmacy_fresh_8_days.sql` для `pharmacy.group_members`, только тело функции): иначе при паузе в 3 суток и карточках раз в неделю товары пропадали бы с сайта. Цена: пропавший из каталога товар висит до 8 суток. Миграцию применить к боевой БД **до** слияния кода (только после подтверждения).
- **Проверено и отброшено:** гипотеза «Rimi перечитывает карточки истёкших акций» не подтвердилась (в последнем прогоне 0 истёкших в списке, ≈1000 карточек за ночь — реально новые акции); объединение мелких заданий и ограничение `match` дают ≈4 мин в сутки, не делали. Запас: Apotheka только по списку, а карточки рецептурных раз в неделю (−1/3 её времени); публичный репозиторий снимает лимит.

## 2.12.0.0 — 2026-11-12
- **Сопоставление: автопринятие пар по двойной проверке Gemini** (шаг C плана). Пара из очереди принимается без админа, только если Gemini назвал её одним товаром И вторая независимая проверка (`checkPrompt`: чем отличаются стороны — вкус, вариант, возраст, размер, форма) не нашла различий. Нет любого из двух ответов — пара остаётся в очереди. Принятые пары не пишутся в `match_decisions`: ответы кэшируются (`grocery.pair_checks`, миграция `20261112100000_pair_checks.sql`, только добавление), решение пересчитывается каждый запуск, поэтому видны во вкладке «Объединённые товары» и снимаются «Убрать из сопоставления» или решением «разные». В предположениях теперь `idsA`/`idsB` (акции каждой стороны), проверка видит обе стороны (до 3 названий с каждой). Матчер пишет в лог «принято по Gemini N».
- **Замер на ручных решениях 12.11** (104 пары, где вердикт Gemini был «тот же»): проверка приняла 71, из них 0 ошибочных (все 5 пар, где админ сказал «разные», она отклонила); отклонила 31, из них 26 админ объединил сам (они остаются в очереди, то есть страховка осторожная). Промпт под выборку не подгонялся. Один Gemini без проверки ошибался в 5 из 104 (95%).
- **Не вошло:** кандидаты-сироты (пары с Жаккаром < 0,6) для Gemini: в вашей выборке все 99 пар «тот же» уже были в очереди, смысла нет, пока очередь не покажет обратное. Боевая БД: миграцию `pair_checks` применить **до** слияния кода (только после подтверждения).

- **Сопоставление: правило сокращений** (шаг A плана улучшения). Ключи одной корзины (бренд | размер | условие), слова которых различаются только сокращением с точкой в названии («koc.» и «kociņa», «mais.» и «maisījums», «vīrieš.» и «vīriešiem») или латышским падежным окончанием («citrona» и «citronu»), объединяются сами.
