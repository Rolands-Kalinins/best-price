# PRD: BestPrice — сравнение акций магазинов Латвии

> Источник: [docs/PLAN.md](../docs/PLAN.md). Документ написан для разработчика, который будет реализовывать проект. Если PRD и PLAN.md расходятся, верным считается PRD.

## 1. Введение / Обзор

BestPrice — закрытый веб-сервис для владельца, его семьи и друзей (не больше 20 человек). Раз в сутки он собирает акции пяти магазинов Латвии (Lidl, Maxima, Barbora, Etop, Rimi) и показывает их на одной странице.

**Проблема.** Чтобы узнать, где сейчас дешевле нужный товар, приходится открывать четыре сайта. У каждого своя вёрстка, свои единицы и свои условия акций («при покупке 2 шт.»), так что цены трудно сравнить напрямую.

**Цель.** Пользователь вводит название товара и сразу видит, в каком магазине он по акции дешевле, с ценой за кг или литр.

Проект некоммерческий: денег не приносит и ничего не должен стоить. Интерфейс на русском, названия товаров остаются в оригинале (на латышском).

## 2. Цели

1. Акции всех четырёх магазинов обновляются автоматически раз в сутки.
2. У каждой акции есть цена за единицу (кг или л), если объём удаётся определить, чтобы товары разной фасовки можно было сравнить.
3. Один и тот же товар из разных магазинов показывается одной карточкой с ценами по магазинам.
4. Войти может любой, у кого есть Google-аккаунт (с 2.8.0.0, решение владельца: данные — публичные цены, личных нет). Аноним без входа не видит ни одной строки данных.
5. Сбой одного парсера не ломает сайт и не мешает работе остальных парсеров.
6. Вся инфраструктура укладывается в бесплатные тарифы: 0 € в месяц.
7. Новый раздел (не продукты) подключается командой `pnpm new-module`, без переписывания ядра.

## 3. Пользовательские истории

### Участник (`member`)

- Как участник, я хочу войти через Google одной кнопкой, чтобы не заводить отдельный пароль.
- Как участник, я хочу найти товар по названию и увидеть цены во всех магазинах, где он сейчас по акции, чтобы выбрать, куда идти.
- Как участник, я хочу видеть цену за кг или литр, чтобы сравнивать упаковки разного размера.
- Как участник, я хочу видеть значок у акций с условием («2 шт.», «с картой»), чтобы не принять их за обычную скидку.
- Как участник, я хочу фильтровать акции по магазину и по значку «с условием», чтобы смотреть только то, что мне подходит.
- Как участник, я хочу видеть, когда обновлялись данные каждого магазина, чтобы понимать, насколько им можно доверять.
- Как участник, я хочу добавлять товары в избранное, чтобы быстро проверять их цены.
- Как участник, я хочу добавлять акции в личный список покупок и отмечать купленное, чтобы взять список с собой в магазин.

### Администратор (`admin`, владелец)

- Как администратор, я хочу управлять белым списком email, чтобы решать, кто получает доступ.
- Как администратор, я хочу видеть очередь неуверенных сопоставлений и подтверждать или отклонять их, чтобы в сравнении не смешивались разные товары.
- Как администратор, я хочу получать письмо, когда парсер падает, чтобы вовремя его починить.
- Как администратор, я хочу видеть историю запусков парсеров, чтобы понимать, какой магазин работает нестабильно.

## 4. Функциональные требования

Требования сгруппированы по этапам в порядке реализации. Этап начинается только после того, как работает предыдущий.

### Этап 1. Каркас

- **FR-1.** Репозиторий должен быть одним приватным monorepo на pnpm workspaces со структурой: `apps/web` (сайт), `packages/core` (общий код и типы), `packages/scrapers/*` (по пакету на каждый магазин).
- **FR-2.** Сайт `apps/web` должен быть написан на Next.js (App Router) с Tailwind и shadcn/ui и разворачиваться на Vercel (тариф Hobby).
- **FR-3.** Система должна использовать Supabase (тариф free) как базу данных Postgres и для авторизации.
- **FR-4.** Система должна позволять входить только через Google OAuth. Входа по паролю или email-ссылке нет.
- **FR-5.** (изменено в 2.8.0.0: открытая регистрация) Любой вошедший через Google автоматически становится `member` и видит все данные кроме админки. Проверка на уровне БД: `is_member()` истинна, если в JWT есть email; аноним не получает ни одной строки, даже через Supabase API напрямую. Белый список `allowed_emails` теперь только назначает роль `admin`.
- **FR-6.** (снято в 2.8.0.0) Экран «Доступ закрыт» остался в `app/page.tsx` как запасной, но недостижим: `is_member()` истинна для любого вошедшего.
- **FR-7.** Система должна поддерживать две роли: `admin` и `member`. Роль хранится в таблице `users`. Админские действия (белый список, очередь сопоставления) доступны только `admin`, проверка в RLS.
- **FR-8.** Система должна иметь общие таблицы ядра:
  - `users`: пользователь, его email и роль;
  - `sources`: магазины-источники (название, URL, раздел, к которому относится источник);
  - `scrape_runs`: журнал запусков парсеров (источник, время начала и конца, статус `success`/`failed`, число полученных товаров, текст ошибки).
- **FR-9.** Запросы к БД должны идти через `supabase-js` со сгенерированными TypeScript-типами. ORM не используется.

### Этап 2. Lidl от начала до конца

- **FR-10.** Система должна иметь отдельную схему БД `grocery` для данных продуктового раздела (акции, товары, история цен, сопоставления).
- **FR-11.** Парсер Lidl должен получать все товары со страницы «Актуальные предложения» (`/c/aktualie-piedavajumi/a10028219`), разбирая JSON из атрибута `data-grid-data`.
- **FR-12.** Парсер Lidl должен сохранять даты начала и окончания акции из источника.
- **FR-13.** Каждый запуск парсера должен записываться в `scrape_runs`, и успешный, и с ошибкой.
- **FR-14.** Парсеры должны запускаться через GitHub Actions по cron раз в сутки в 06:00 по времени Риги. Должен работать и ручной запуск через интерфейс GitHub (`workflow_dispatch`).
- **FR-15а.** Админ должен видеть в интерфейсе (`/grocery/admin/scrapers`) статус каждого парсера (последний запуск, результат, длительность, ошибка), время и обратный отсчёт до следующего запуска по расписанию и запускать один или все парсеры вручную. Обычный участник этого не видит: `scrape_runs` закрыта RLS для всех, кроме админа. Статус: сделано (1.8.0.0), кроме состояния «выполняется сейчас».
- **FR-15.** Если парсер завершился ошибкой, workflow GitHub Actions должен завершаться со статусом failure, чтобы GitHub прислал владельцу письмо.
- **FR-16.** Сайт должен показывать страницу со списком текущих акций Lidl: название, цена, старая цена (если есть), даты акции.
- **FR-17.** У каждого магазина на сайте должна быть метка «обновлено X назад» по времени последнего успешного запуска из `scrape_runs`.
- **FR-18.** На этом этапе нужно проверить, не блокирует ли Lidl запросы с IP GitHub Actions, и записать результат (см. «Открытые вопросы»).

### Этап 3. Остальные магазины

- **FR-19.** Все парсеры должны реализовывать один общий контракт из `packages/core`: на входе ничего, на выходе массив акций одного формата (название, бренд, объём, цена, старая цена, единица, условие, даты, EAN, URL, категория магазина). Формат описан zod-схемой.
- **FR-20.** Парсер Maxima должен получать все акции одним запросом `GET /ajax/salesloadmore?limit=5000` (limit с запасом: акций 1136 на 2026-10-27 и их число растёт), разбирать плитки из ответа, а даты брать из `data-dates-interval`. Акция «−N% на бренд или категорию» (без цены) сохраняется с `discount_percent` и пустым `price`. Цена по карте PALDIES сохраняется с условием «Ar PALDIES karti». Статус: реализовано, парсер не запущен на боевой БД (миграция `20261025120000` не применена).
- **FR-21.** Парсер Etop должен получать все акции сайта (1402 на 2026-10-28, типы 3, 9, 18, 21) через JSON `POST /v1/Products/GetPromotionProducts` страницами по 500 до `hasMore:false`. Парсер должен сохранять EAN, категорию и даты акции; цену по карте top! сохранять с условием «Ar top! karti». Каталога без акций у Etop нет. Статус: реализовано, проверено живым прогоном без записи в БД; на боевой БД и в GitHub Actions не запущено.
- **FR-22.** Парсер Rimi должен обходить `/e-veikals/lv/akcijas-piedavajumi?pageSize=100&currentPage=N` несколько раз (порядок на сервере нестабилен) и сохранять все плитки: со старой ценой, с ценой по карте MansRimi (условие «Ar MansRimi karti»), «N un vairāk», «Ja liec grozā N» (цена за N штук) и EDLP. Период действия берётся с карточки товара, категория (код `SH-…`) с плитки. Статус: реализовано, на боевой БД не запущено.
- **FR-23.** Условие акции («2 шт.», «ar karti» и т. п.) должно храниться текстом в поле `condition`. Если условия нет, поле пустое.
- **FR-24.** Система должна рассчитывать цену за единицу (за кг или за л) по цене и объёму товара. Если объём определить нельзя, цена за единицу не показывается, и товар от этого не ломается.

### Общие правила парсеров (все этапы)

- **FR-25.** Парсер должен делать не больше одного запроса в секунду к одному магазину.
- **FR-26.** Парсер должен отправлять честный User-Agent, например `BestPriceBot (личный проект)`, и соблюдать `robots.txt` магазина.
- **FR-27.** Парсер не должен обходить защиту сайта (Cloudflare challenge, капчу, ограничения по IP). Если магазин блокирует честный запрос, парсер отключается, а магазин помечается как «ручной режим / позже».
- **FR-28.** Ответы магазина должны кэшироваться в пределах одного запуска, чтобы одна страница не запрашивалась дважды.
- **FR-29.** Все данные от парсера должны проходить валидацию zod до записи в БД. Невалидные записи не пишутся, их количество попадает в лог запуска.
- **FR-30.** При сбое парсер должен сохранять сырые ответы магазина как артефакт GitHub Actions со сроком хранения 7 дней. В БД сырые данные не попадают никогда.
- **FR-31.** Если GitHub Actions блокируется магазином, этот парсер должен уметь запускаться с ПК владельца (Windows Task Scheduler) той же командой и писать в тот же Supabase.
- **FR-32.** Playwright можно использовать только для магазина, который без него не открывается. По умолчанию используются `fetch` + cheerio.

### Жизненный цикл акций и история цен

- **FR-33.** Если у акции есть дата окончания (Lidl, Maxima, Etop), после этой даты сайт должен её скрывать.
- **FR-34.** Если дат нет (карточка Rimi не открылась), акция считается действующей, пока товар находится в ежедневном запуске. Как только товар пропал из успешного запуска, акция закрывается. Неуспешный запуск акции не закрывает.
- **FR-35.** Система должна хранить историю цен: не больше одной строки в день на пару «товар + магазин», и строка пишется только при изменении цены.
- **FR-36.** Система должна удалять строки истории цен старше 6 месяцев (ежедневная автоматическая очистка).

### Этап 4. Сопоставление товаров и главная страница

- **FR-37.** Если у товаров из разных магазинов совпадает EAN, система должна сразу считать их одним товаром, без админ-очереди.
- **FR-38.** Если EAN нет, система должна нормализовать бренд, название и объём (регистр, диакритика, единицы: `1l` = `1000 ml`) и сравнивать их нечётким поиском (fuzzy).
- **FR-39.** Совпадение с высокой уверенностью система должна подтверждать автоматически. Совпадение с низкой уверенностью должно попадать в админ-очередь. Пороги задаются константами в коде.
- **FR-40.** В админ-очереди администратор должен видеть два товара рядом (название, бренд, объём, магазин, фото, если оно есть) и кнопки «Это один товар» и «Разные товары».
- **FR-41.** Решение администратора должно запоминаться: та же пара товаров не должна повторно попадать в очередь при следующих запусках.
- **Статус FR-37…FR-41 (2026-10-28, версия 1.3.0.0):** реализовано без EAN-шага между магазинами (EAN есть только у Etop, сопоставлять не с чем) и без fuzzy-порога: автоматически объединяются только точные совпадения нормализованного ключа «бренд | размер | условие | слова», а пары с долей общих слов ≥ 0,6 (Жаккар) идут в очередь `/grocery/admin/matches`. Решения хранятся по ключам пары. Решение применяется при следующем запуске `match` (после парсеров или вручную `gh workflow run match.yml`).
- **Дополнение к FR-38 (2026-10-28, версия 1.5.0.0):** бренд для акций без него определяет Gemini по названию (принимается, только если слово есть в названии), результат кэшируется; в очереди FR-40 у предположения есть совет модели («вероятно тот же / разные» с причиной), решение остаётся за админом. Подробности: `docs/PLAN.md`, п. 6 «Сопоставление товаров».
- **Дополнение к FR-40 (2026-10-28):** у каждой акции в очереди есть кнопка «Убрать из сопоставления» (убранные видны внизу с «Вернуть»), фото увеличивается нажатием.
- **FR-42.** (Изменено 2026-10-28, версия 1.7.0.0; раньше: «общих категорий нет».) У каждой акции должна быть общая категория (~20 крупных: мясо и рыба, молочные продукты, хлеб, овощи и фрукты, напитки, бытовая химия и т.д., плюс «Другое») и фильтр по ней на главной странице. Категории задаёт словарь в коде, а не Gemini на каждый товар. **Статус:** реализовано, подробности и ограничения точности в `docs/PLAN.md` («Данные продуктов»). Отложено: автоматическая проверка точности, перераспределение «Другое» через Gemini.
- **FR-43.** Главная страница продуктового раздела должна содержать:
  1. поиск по названию товара;
  2. для сопоставленных товаров карточку «товар → цены в магазинах» с ценой за единицу, отсортированную по цене за единицу;
  3. для несопоставленных список свежих акций, сгруппированный по магазинам.
  - *Статус:* пункт 1 и общая лента акций реализованы (`/grocery`: поиск, сетка карточек с фото). Сейчас лента одна общая, без группировки по магазинам (см. `docs/PLAN.md`, «Фронтенд»); пункт 2 реализован как секция «Где дешевле» над лентой (товары минимум в двух магазинах, самая дешёвая цена сверху, разница в € и %; фильтр по магазину, условию или скидке показывает акции как есть). Группировка несопоставленных по магазинам (пункт 3) не нужна: они остаются в общей ленте.
- **FR-44.** На главной должны быть фильтры по магазину и по признаку «с условием». *Статус: реализовано, плюс сортировка; состояние в URL.*
- **FR-45.** Товары с непустым `condition` должны помечаться значком. При наведении или нажатии на значок виден текст условия. *Статус: значок сразу содержит текст условия на карточке, подсказка не нужна.*

### Этап 5. Персональное

- **FR-46.** Пользователь должен иметь возможность добавить товар в избранное и убрать его оттуда.
- **FR-47.** Пользователь должен иметь возможность добавить акцию из каталога в личный список покупок, отметить её купленной и удалить. Вписывать товары в список свободным текстом нельзя.
- **FR-48.** Если акция из списка покупок закончилась, она остаётся в списке, но помечается «акция закончилась».
- **FR-49.** Избранное и список покупок у каждого пользователя свои. Другие пользователи, включая `admin`, не видят чужие записи (RLS по `user_id`).

### Этап 6. Расширяемость

- **FR-50.** Разделы сайта (сейчас только «Продукты») должны подключаться через один файл-реестр. Добавление раздела в реестр показывает его в навигации, удаление скрывает.
- **FR-51.** Команда `pnpm new-module <имя>` должна создавать шаблон нового раздела: SQL-миграцию для схемы `<имя>.*`, модуль во фронтенде, пакет парсера `packages/scrapers/<имя>` по общему контракту и запись в реестре.
- **FR-52.** Раздел, созданный генератором, должен собираться и показываться на сайте без ручных правок ядра.

### Этап 7. Буклеты магазинов

- **FR-53.** Система должна читать акции из рекламных буклетов магазинов (Gemini по картинкам страниц) и хранить их в отдельной таблице `grocery.leaflet_offers`, не смешивая с акциями сайта. *Статус: реализовано для Lidl в 1.9.0.0 (job `lidl` в `scrape.yml` читает буклет, парсер сайта Lidl отключён); на сайте не показывается.*
- **FR-54.** Данные буклета должны проходить проверку: запись без цены у товара, с нелепой ценой или с процентом скидки, не сходящимся с ценами, отбрасывается и попадает в лог. *Статус: реализовано.*
- **FR-55.** Цены буклета и цены сайта одного магазина должны сравниваться между собой (часть совпадёт, у буклета больше товаров). *Статус: не реализовано.*
- **FR-56.** Буклеты Etop, Maxima и Rimi должны читаться так же, как у Lidl. *Статус: не реализовано; источники найдены (см. `docs/PLAN.md`, «Буклеты магазинов»).*
- **FR-58.** У позиций буклета должны быть картинки товаров, вырезанные из страницы по рамке от Gemini. *Статус: реализовано в 1.9.0.0: миниатюры в `leaflet_thumbs`, на сайте и в админке.*
- **FR-62.** Barbora (интернет-магазин Maxima) должна быть отдельным магазином: парсер забирает акции для всех и цены по карте Paldies из внутреннего JSON-API, пропускает позиции без наличия, приводит условия к формату остальных магазинов, чтобы одинаковый товар Barbora и Maxima склеивался в одну плитку «где дешевле», и сохраняет категорию полным путём по дереву сайта. *Статус: реализовано в 1.11.0.0 (3060 акций на 2026-10-31, локально проверено), в боевую БД не применено; таблица соответствия категорий Barbora и наших категорий не сделана.*
- **FR-61.** Администратор должен видеть список акций магазина и править название, бренд, объём, условие, цены, срок и картинку; правка не должна затираться парсером. Меню админки боковое. *Статус: реализовано в 1.10.0.0 (`/grocery/admin/offers`, `locked_fields`); картинка только ссылкой.*
- **FR-60.** Акции Lidl на главной странице должны браться из буклета в том же виде, что у остальных магазинов (лента, категории, сравнение цен). *Статус: реализовано в 1.9.0.0 зеркалированием `leaflet_offers` в `offers`; проверено на локальной БД, в боевой не включено до слияния.*
- **FR-59.** Повторяющиеся позиции буклета (один товар на нескольких страницах, варианты с разной ценой) должны объединяться при показе. *Статус: не реализовано, способ описан в `docs/PLAN.md`.*
- **FR-57.** Администратор должен видеть страницу буклета рядом с таблицей прочитанных из неё записей (номер, название, цены, процент, условие, срок), чтобы сверять результат Gemini с оригиналом. *Статус: просмотр реализован в 1.9.0.0 (`/grocery/admin/leaflet`); правка записей не сделана.*

- **FR-63.** Аптеки (Mēness, Euroaptieka, Benu, Apotheka) и косметика (Douglas; Drogas отложен) собираются **полным каталогом**, а не только акциями, в отдельные схемы `pharmacy.*` и `cosmetics.*`. Цель: найти один и тот же товар в разных магазинах группы и показать самую низкую цену. *Статус: Mēness (10 220 товаров), Euroaptieka (6 602), Benu (6 070) и Apotheka (7 761) реализованы, Douglas не начат.*
- **FR-64.** Рецептурный препарат помечается флагом `prescription`, а не отбрасывается. *Статус: флаг и разбор есть; у Mēness рецептурных на сайте не оказалось (0 из 10 220); у Benu рецептурные (1 418) есть в индексе, но со статусом «new» и без наличия, в выборку «в наличии» не попадают.*
- **FR-65.** Товары аптек раскладываются по смысловым категориям (лекарства без рецепта, БАДы и витамины, чаи и питание, гигиена, косметика и уход, мама и ребёнок, медтовары, зоотовары), каждая привязана к продуктовой категории для сравнения с продуктовыми магазинами. *Статус: реализовано (`core/pharmacy-categories.ts`).*
- **FR-66.** Магазин, который блокирует парсер, снимается с сайта; защиту не обходим. *Статус: правило владельца от 2026-11-01.*

- **FR-68.** Для товаров аптек сохраняется цена по карте магазина (клуб Euroaptieka, «Veselība» Mēness) отдельно от цены для всех, с условием и сроком (например, «при покупке от 9 EUR»). *Статус: реализовано в 2.1.0.0: Mēness 775 товаров, Euroaptieka 131.*

## 6. Дизайнерские решения

- Компоненты из shadcn/ui, стили на Tailwind. Своих UI-библиотек не делаем.
- Интерфейс на русском. Названия товаров, бренды и категории показываются как в источнике (на латышском), без перевода.
- Сначала вёрстка под телефон: сайтом будут пользоваться в магазине.
- Цены в евро в формате `1,29 €`, цена за единицу мелким шрифтом под основной: `2,58 €/кг`.
- Значок «с условием» — заметная небольшая пометка рядом с ценой, текст условия во всплывающей подсказке.
- Метка «обновлено X назад» видна рядом с названием каждого магазина. Если данные старше 2 суток, метка выделяется цветом-предупреждением.
- Визуальные решения: зелёный акцент (выгода), тёплый красный только для скидки; светлая и тёмная темы по системным настройкам; шрифт Inter; сетка карточек с фото. Подробности в `docs/PLAN.md`, «Фронтенд».
- Метка «обновлено X назад» реализована, но выделение цветом при данных старше 2 суток пока нет.

## 7. Технические соображения

- **Изоляция отказов.** Каждый парсер — отдельный пакет и отдельный шаг (или job) в GitHub Actions. Ошибка одного не должна останавливать остальные. Сайт читает только БД и от парсеров напрямую не зависит.
- **Часовой пояс cron.** GitHub Actions задаёт cron в UTC. 06:00 по Риге соответствует 03:00 UTC зимой и 04:00 UTC летом. Выберите одно значение (или запускайте в оба часа и пропускайте лишний запуск) и опишите выбор в README.
- **Секреты.** Ключ Supabase `service_role` для записи из парсеров хранится только в GitHub Secrets и в локальном `.env` владельца. Во фронтенд и в репозиторий он не попадает.
- **Типы БД.** После каждой миграции нужно перегенерировать TypeScript-типы Supabase и закоммитить их.
- **Валидация.** zod-схема акции лежит в `packages/core` и общая для всех парсеров.
- **Бесплатные лимиты.** Supabase free (БД до 500 MB; проект приостанавливается при долгой неактивности), Vercel Hobby (только некоммерческое использование), GitHub Actions для приватного репозитория (ограниченный бесплатный запас минут в месяц). Парсеры должны быть быстрыми: без Playwright там, где он не нужен.
- **Maxima за Cloudflare.** Вероятнее всего, именно она заблокирует GitHub Actions, поэтому для неё заранее предусмотрен запуск с ПК владельца (FR-31).
- **Зависимости.** Next.js, Tailwind, shadcn/ui, `@supabase/supabase-js`, cheerio, zod. Playwright добавляется только при необходимости. Библиотеку для fuzzy-сравнения выбирает разработчик на этапе 4.

## 8. Метрики успеха

1. **Надёжность парсеров.** Не меньше 90% успешных ежедневных запусков каждого включённого парсера за последние 30 дней. Считается по таблице `scrape_runs`.
2. **Свежесть данных.** Ни у одного включённого магазина последний успешный запуск не старше порога расписания магазина (самая длинная пауза плюс сутки: 48 часов у ночных, 96 у Rimi и аптек, 192 у Lidl) дольше двух дней подряд.
3. **Нулевая стоимость.** Ежемесячный счёт за Vercel, Supabase и GitHub — 0 €. Размер БД держится заметно ниже лимита Supabase free (ориентир: меньше 400 MB). Минуты GitHub Actions укладываются в бесплатный запас.
